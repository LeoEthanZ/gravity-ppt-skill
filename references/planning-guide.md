# 大模型内容理解与逐页规划

本文件只用于生成前规划。规划阶段不得写 HTML，也不得改写、总结或补充原文。

## 1. 建立源内容模型

完整读取源文件和全部素材，先按原顺序建立 `source_units`。每个单元包含：

- `id`：稳定唯一 ID，例如 `u001`。
- `type`：`heading`、`paragraph`、`list`、`table`、`image_group`、`caption`、`person_bio`、`quote`、`process` 或 `task`。
- `source_range`：源文件起止行。
- `text`：原文；图片单元可为空。
- `parent_heading`：最近的原文标题。
- `image_ids`：该单元直接包含或绑定的图片 ID。
- `required`：是否必须在正文页呈现；默认 `true`。
- `original_order`：该完整内容单元在源文档中的顺序。
- `planned_order`：完成受控重排后的演示顺序；无移动时与 `original_order` 相同。
- `top_level_id`：该单元所属的一级章节 ID；用于禁止跨章移动。

同时建立：

- `images`：每张图的 ID、源路径、源行、尺寸、比例和前后文字。
- `allowed_titles`：源文档真实存在、可用作页面标题的标题集合。
- `relationships`：标题归属、顺序关系、表格结构、图片说明和人物—肖像关系。

人物连续介绍不能按“图片在段落之后”机械绑定。检查前后姓名标题、肖像位置和人物顺序；图片紧邻下一位人物标题时，优先判断其属于下一位人物。

## 2. 建立三层层级映射

不能机械照搬 Markdown 的 `# / ## / ### / ####`，也不能为了版式随意升级或降级标题。规划前必须同时理解三层结构：

- **文档层级**：源文件真实存在的标题级别和前后位置。
- **语义层级**：章节、主题、子主题、标签、例证、说明、图片标签、人物或案例归属。
- **演示层级**：目录章节、小节幕封、页标题、页内分组标题或普通正文。

建立顶层 `hierarchy_map`，源文档中的每个标题恰好登记一次，至少包含：

- `id`：层级节点 ID。
- `source_unit_id`：对应的标题源单元。
- `source_level`：源文件中的真实标题级别，取 `1`–`6`。
- `semantic_role`：`chapter`、`topic`、`subtopic`、`label`、`example`、`note`、`person` 或 `case`。
- `presentation_role`：`toc_chapter`、`section`、`page_title`、`group_title` 或 `body`。
- `parent_id`：语义父节点；顶层为 `null`。
- `top_level_id`：所属一级章节；一级节点指向自身。
- `reason`：为何采用该语义角色和演示角色。

判断原则：

- 无直接正文的父标题可作为目录章节、章节导航或页内分组依据，不得因此制造空内容页。
- 短标签、图片标签、人物姓名和案例小标题通常应下沉为页内分组标题，不自动成为独立页面。
- 多个同级短块可以在共同父标题下合并成一页，但仍保留每个原文标题和完整内容单元。
- 常规课程层级默认映射为：一级标题 → `toc_chapter` / `section`，二级标题 → `page_title`，三级标题 → `group_title`，四级及以下 → `group_title` 或 `body`。页面存在二级父标题时，三级标题不得升级为黑色页标题；二级标题作为页标题后不得在正文中重复渲染。
- 只有真正承担一级叙事转场的标题才使用 `section`；Markdown 级别本身不是充分条件。
- 标题的演示角色可以与文档级别不同，但必须记录判断理由，且不能改变其语义父子关系。

## 3. 理解内容类型

逐个判断内容的真实结构，不从普通段落中发明结构：

- `👉`、`→`、箭头或连续编号连接多个节点：`process`，优先 C07。
- 原始时间节点：时间线，C06。
- 原始表格：C09；保留全部行列和单元格。
- 一段正文与一张主图：C01/C02。
- UI 操作教程先建立 `step_text ↔ screenshot` 一一关系；将每个步骤与对应界面截图视为一个不可拆分单元。截图中的步骤标记、界面状态以及前后步骤文本共同决定归属，不能只按图片在 Markdown 中的位置机械绑定。
- 上方说明与宽图或横向图库：C03。
- 真实存在的 3–4 组同级内容：C04。
- 原文列表、履历、注意事项：C14。
- 单张主视觉或以图片为主：C13。
- 只有原文明确存在相应结构时，才使用 C05、C08、C10、C11、C12、C15、C16、C17、C18。

小型 Logo、工具图标和头像缩略图要比较横排与纵排；纵排导致图像很小或大量空白时优先横排。卡片文字量不均时，长卡优先跨列或扩大容器。

## 4. 受控重排完整内容单元

默认保持源文档顺序。只有在能明确改善内容归属、阅读顺序或页面组合时，才允许在**同一一级章节或同一语义父节点内**有限移动完整内容单元。

允许的场景：

- 把图片移动到真正对应的人物、案例或段落旁。
- 把图片标签、短说明与其图片或表格合并。
- 把共同父标题下的同级短块合并，避免短标题或一两个词独占页面。
- 为避免孤页，将相邻且语义兼容的完整单元前移或后移。
- 调整父标题与其实际所属内容的贴合位置，但不改变原有父子含义。

禁止的场景：

- 跨一级章节移动。
- 拆句重组、截取半个列表项、拆散表格行列或把多个原句拼成新句。
- 改变因果、时间、步骤、对照、人物、图片或案例对应关系。
- 将不同小节的图片集中成与原文无关的图库。
- 仅为视觉对称、填满页面或减少页数而改变原意。

顶层必须存在 `reorder_log`；没有移动时使用空数组。每条记录至少包含：

```json
{
  "unit_id": "u012",
  "original_order": 12,
  "planned_order": 10,
  "move_type": "attach_to_related_image",
  "move_reason": "图片与人物标题存在前向归属关系",
  "source_parent": "h02",
  "planned_parent": "h03"
}
```

每个发生位置变化的单元都必须登记。`move_reason` 必须说明语义依据，不能只写“为了美观”“为了排版”或“空间不足”。移动只改变完整单元的位置或展示父节点，不改变单元文字。

## 5. 规划页面

按照 `planned_order` 组合相邻、同主题、版式兼容的单元。不要一单元一页，也不要把不相干内容仅因版式相同放在一起。

`pages` 是 A 模式唯一的分页事实来源。创建它时由大模型逐页判断语义、容量和素材归属；生成 HTML 的代码只能遍历 `pages`，不得再实现“遇到标题/图片/表格/代码就换页”的第二套分页逻辑。渲染发现问题时先修改规划并重新校验，不得只在 HTML 中临时合页或拆页。

每页包含：

- `page_no`
- `chapter`
- `title`：必须来自 `allowed_titles`，连续页保持完全相同。
- `content_type`
- `layout`：`C01`–`C18` 或 `section`。
- `source_unit_ids`
- `image_ids`
- `estimated_fill`：`0`–`1`。
- `reason`：为何这样组合、为何选择该版式。
- `density_exception`：仅章节页、原文金句、主视觉或用户指定留白页可用。

密度规则：

- 普通页面预计占用率低于 `0.25` 时，继续尝试合并相邻内容。
- 超过 `0.85`、文字需过度缩小、表格或图片不可读时拆页。
- 表格不能按固定行数机械拆分；根据说明高度、单元格文字量和真实可用高度决定，能放在上一页就不另起页。
- 标题、短标签、一两个词、图片前缀不能独占页面。
- 同一二级标题下的短“概念说明”和“特点/用途/优势”优先合页；若下一页也是短文本且合并后不超过容量，应在规划阶段合并，而不是依赖生成后的 CSS 填补空白。
- 用户要求 UI 教程一步一页时，每页 `source_unit_ids` 必须只包含该步骤文字、其对应截图以及必要的共同三级标题；下一步骤文字与截图同时移动到下一页。
- 二级及以下标题不触发分页；标题至少与一个所属正文、列表、表格或图片单元同页。父标题本身无直接正文时可仅作为页内层级信息，不为保存该标题而生成空页。
- 有序列表单元记录 `list_start` 或等效原始序号。跨单元、跨页和截图交错后仍按源文档编号继续，不得把每个列表块重置为 1。
- 连续页不添加“续”“（续）”或英文后缀。

## 6. 规划审计

写 HTML 前确认：

1. 每个 `required: true` 的源单元恰好出现在一页。
2. 每张图片恰好出现在一页，并与正确文字或人物绑定。
3. 每个页面标题都来自 `allowed_titles`，没有续页后缀。
4. 非例外页面占用率处于 `0.25–0.85`。
5. 版式由真实内容类型触发，不需要模型补写观点、步骤、数字、结论或图片说明。
6. 表格、卡片和图片组已比较真实剩余空间与候选排列。
7. 每个标题已完成文档层级、语义层级和演示层级映射。
8. 所有顺序或父节点变化均已写入 `reorder_log`，且没有跨一级章节。
9. 按 `planned_order` 阅读仍保持原有因果、时间、步骤、人物和图片归属。
10. 不存在仅因二三级标题、图片、表格、代码块或 Markdown 块边界产生的页面切分。
11. Obsidian 嵌入素材已先于表格分列解析；`![[name.svg\|64]]` 中的转义竖线没有被误判为单元格边界。
12. 用户授权截取的长示例已记录授权与展示范围；未授权内容仍完整覆盖。

运行：

```bash
node scripts/validate-page-plan.mjs page-plan.json
```

规划失败时先修正 JSON；不要通过跳过单元、删除图片或编造文案让校验通过。

## 7. 生成与回查

规划通过后才生成 HTML。生成结束后逐页对照 `page-plan.json`：页面顺序、标题、内容单元、图片、版式必须一致。视觉调整可以改变容器尺寸、网格和字号，但不得改变内容归属或原文。

在 1920×1080 真实浏览器中逐页检查溢出与低密度。低密度必须依据渲染后的主体边界或截图判断，不能复用 `estimated_fill`。模板不支持 URL hash 跳页时，使用真实导航按钮、键盘事件或模板 `go()`；等待过渡动画完成后再截图或测量。检查本地图片 `naturalWidth > 0`，并抽查所有 SVG、跨页有序列表和长示例截取页。发现分页问题时回到 `pages` 修正并重新运行规划校验。
